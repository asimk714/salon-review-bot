# Architecture

## Overview

Lakme Salon Review Assistant is a client-side React app that drafts honest Google reviews from structured user input. The AI call happens server-side in a Supabase Deno edge function, so the AI API key never reaches the browser.

The system has three parts:

1. **Frontend** — React + Vite + shadcn/ui. Runs in the browser.
2. **Supabase client** — connects the frontend to Supabase (edge functions + env).
3. **Deno edge function** — validates input, calls the AI gateway, returns a structured JSON draft.

---

## Frontend architecture

- **Vite** handles bundling and the dev server.
- **React 18** with functional components and hooks.
- **TypeScript** throughout.
- **shadcn/ui** provides accessible Radix-based primitives (button, card, select, textarea, label, toast, tooltip). About 10 are used; the rest remain in the repo as available primitives.
- **React Router** provides a single `/` route plus a `*` catch-all 404 page.
- **React Query** (`@tanstack/react-query`) is installed but not heavily used — the edge function is invoked directly via `supabase.functions.invoke()` rather than through React Query's mutation hooks.
- **Tailwind CSS** for styling, with custom CSS variables for the design tokens (colors, radius, fonts).
- **Playfair Display** (serif) for headings, **Inter** (sans) for body — both loaded from Google Fonts.

### Key components

- `pages/Index.tsx` — root page, manages app state (form / loading / results), form persistence in localStorage, submit and regenerate handlers.
- `components/ReviewForm.tsx` — form with rating radiogroup, visit type select, two textareas (what stood out, what to tell others), two optional fields (staff name, context). Owns validation (all 4 required fields must be filled).
- `components/ResultsScreen.tsx` — renders trust banner, editable review cards (short + detailed variants), star display of the user's rating, copy and copy+open-Google buttons, regenerate button, and a collapsible "what this draft was based on" transparency section.
- `components/Header.tsx` — app title, subtitle, salon logo image (loaded from an external CDN).
- `components/StatsNote.tsx` — one-line honest note about data handling (replaced the old fabricated-stats `StatsBar`).
- `components/Footer.tsx` — disclaimer + author credit.

### State model

The app has three states: `form`, `loading`, `results`. Form data is persisted to `localStorage` under the key `lakme-review-form` so a page refresh mid-draft doesn't lose the user's answers. The form data shape is:

```ts
interface FormData {
  rating: number;        // 1-5
  visitType: string;     // from predefined list
  stoodOut: string;      // user's own words
  tellOthers: string;    // user's own words
  staffName: string;     // optional
  context: string;       // optional
}
```

## Supabase integration

Supabase is used for two things:

1. **Client SDK** — the frontend creates a Supabase client from `VITE_SUPABASE_URL` and `VITE_SUPABASE_PUBLISHABLE_KEY` (both `VITE_`-prefixed, so Vite exposes them to the browser). This client is used only to invoke the edge function via `supabase.functions.invoke()`. No Postgres tables are queried — the schema currently has zero tables.
2. **Edge function hosting** — the `generate-review` function runs as a Deno edge function inside Supabase. The frontend invokes it; the function runs server-side.

The Supabase types (`src/integrations/supabase/types.ts`) are currently empty (no tables defined). They are generated by `supabase gen types typescript` and would be populated if tables are added later.

## Edge function

**File:** `supabase/functions/generate-review/index.ts`

The function is a Deno HTTP server (using `https://deno.land/std@0.168.0/http/server.ts`). It handles one `POST` path (invoked by the Supabase client).

### Flow

1. Handle `OPTIONS` preflight (CORS).
2. Parse JSON body.
3. Destructure `rating`, `visitType`, `stoodOut`, `tellOthers`, `staffName`, `context`.
4. Validate required fields (`visitType`, `stoodOut`, `tellOthers` must be present). Return `400` with a clear error if missing.
5. Read `LOVABLE_API_KEY` from `Deno.env.get("LOVABLE_API_KEY")`. Throw if missing (config error).
6. Build the system prompt and user prompt.
7. Call the Lovable AI gateway (`https://ai.gateway.lovable.dev/v1/chat/completions`) with:
   - Model: `google/gemini-2.5-flash`
   - System + user messages
   - A forced tool call (`return_reviews` function) with a strict JSON schema (`short` + `detailed`, no additional properties)
8. Handle HTTP errors from the gateway:
   - `429` → rate-limit message
   - `402` → credits-exhausted message
   - other errors → generic "AI gateway error"
9. Parse the tool-call result. If the tool call is present, parse `tool_call.function.arguments` as JSON.
10. Fallback: if no tool call, parse the message content directly (strips markdown fences, then `JSON.parse`).
11. Return `{ short, detailed }` as JSON.
12. On any catch, return a `500` with a generic error message (no internal details leaked to the client).

### Request shape (from frontend)

```json
{
  "rating": 4,
  "visitType": "Haircut",
  "stoodOut": "...",
  "tellOthers": "...",
  "staffName": "Priya",
  "context": "First time visiting"
}
```

### Response shape

```json
{
  "short": "1-2 sentence review",
  "detailed": "3-5 sentence review"
}
```

Both fields are always strings. The frontend reads `result.short` and `result.detailed`.

## AI gateway and model interaction

The edge function calls the **Lovable AI gateway** at `https://ai.gateway.lovable.dev/v1/chat/completions`. This is an OpenAI-format API that the Lovable platform provides, backed by Gemini 2.5 Flash.

### Why tool-call structured output

The prompt asks the model to return a specific JSON shape (`{"short": "...", "detailed": "..."}`). Rather than relying on the model to output clean JSON in its text, the function uses OpenAI-style **tool calls**:

- A `return_reviews` function is defined with a strict JSON schema.
- `tool_choice` is forced to that function.
- The gateway is expected to return a tool call with the reviews as `function.arguments`.
- The function parses `tool_call.function.arguments` as JSON.

This is more reliable than scraping the message content, because the tool-call path enforces the schema at the API level. The content fallback exists for gateways or models that don't support tool calls cleanly.

### Model choice

`google/gemini-2.5-flash` — chosen for speed and cost. Fast enough for an interactive draft flow. Not the most capable model, but adequate for short review drafting from constrained input.

## Data and request flow

```
User's browser
  │
  │ 1. User fills form, taps "Draft My Review"
  │
  ▼
  │ 2. Index.tsx calls supabase.functions.invoke("generate-review", { body: formData })
  │
  ▼
Supabase edge network
  │
  │ 3. Request routed to generate-review Deno function
  │
  ▼
Deno edge function
  │
  │ 4. Validates required fields (400 if missing)
  │ 5. Reads LOVABLE_API_KEY from Deno.env (server-side)
  │ 6. Builds prompts
  │ 7. HTTP POST to Lovable AI gateway
  │
  ▼
Lovable AI gateway → Gemini 2.5 Flash
  │
  │ 8. Returns structured tool call with { short, detailed }
  │
  ▼
  │ 9. Edge function returns JSON to frontend
  │
  ▼
Frontend
  │
  │ 10. Sets shortReview + detailedReview state
  │ 11. Transitions to "results" state
  │ 12. Renders editable results screen
```

No user data is stored in a database. The form data goes from browser → edge function → AI gateway → back. It is not persisted.

## Error handling

### Frontend errors

- **Network / invoke error:** caught in `handleSubmit` and `handleRegenerate`, shows a destructive toast ("Couldn't draft right now", "Regeneration failed"), returns to form (on submit failure) or stays on results (on regenerate failure).
- **Edge function returns `{ error: "..." }`:** treated as a failed response, throws an Error with the message.
- **Malformed AI response:** the content fallback does a `JSON.parse` — if that throws, the error propagates to the catch block and the user sees a generic error toast.

### Edge function errors

- **Missing required fields:** `400` with a descriptive message.
- **Missing `LOVABLE_API_KEY`:** throws, caught by the outer catch, returns `500`.
- **429 from AI gateway:** `429` with rate-limit message.
- **402 from AI gateway:** `402` with credits-exhausted message.
- **Other non-200:** logs the status + body to console, returns `500` with a generic message.
- **JSON parse failure in either path:** caught by outer catch, returns `500`.

The edge function does not expose AI gateway error bodies to the client beyond the status-specific messages.

## Environment and secrets model

### Frontend (browser-exposed, safe)

These are `VITE_`-prefixed and embedded into the built JS bundle:

- `VITE_SUPABASE_URL` — Supabase project URL. Not a secret.
- `VITE_SUPABASE_PUBLISHABLE_KEY` — Supabase anon/publishable key. Intended for the browser. Grants access governed by RLS. Not a service-role key.
- `VITE_SUPABASE_PROJECT_ID` — project identifier. Not a secret.

### Server-side (never in frontend bundle)

- `LOVABLE_API_KEY` — the AI gateway API key. Read by the edge function via `Deno.env.get("LOVABLE_API_KEY")`. Set in Supabase Dashboard → Edge Functions → Environment Variables. Not present in any frontend file.

### `.env` handling

- `.env` is gitignored (added in Phase 3A).
- `.env.example` documents the variable names with placeholders.
- The committed `.env` from an earlier commit has been removed from the index but remains in git history (blob `4da91367fee2c5c302646ec852e8c9eb393f9f85`). See Phase 3A for rotation recommendation.

## Architectural decisions

### 1. Server-side AI call

The AI key could have been called directly from the browser. That would expose the key in the bundle and make it trivial to extract. Calling server-side in a Supabase edge function keeps the key hidden and lets the function handle validation, error mapping, and prompt construction in one place.

### 2. Structured tool-call output over free-text parsing

The prompt asks for JSON, but LLMs don't always return clean JSON. Forcing a tool call with a strict schema is more reliable than regex-parsing the message content. The content fallback is a safety net, not the primary path.

### 3. Constrained user input over free text

The form captures structured fields (rating, visit type, what stood out, what to tell others) rather than a single free-text box. This limits what the AI can invent — it can only work with what the user provided — and produces more consistent, reviewable output.

### 4. No database / no persistence

Reviews are not stored. The only persistence is the form draft in `localStorage` (so a refresh doesn't lose in-progress answers). This keeps the data model simple and avoids privacy questions about storing user reviews.

### 5. Manual Google posting

The app does not post to Google. It copies text and opens the Google review page. This avoids the complexity and trust issues of automating a Google Business Profile API integration, and it keeps the user in control of the final post. It also means the app doesn't need Google OAuth or the My Business API.

### 6. No auth

There is no login. The app is a simple tool, not a platform. Anyone with the link can use it. This avoids the complexity of Supabase auth, user tables, and row-level security for user data — at the cost of no per-user persistence or multi-user features.

## Current limitations

- Single hardcoded salon place ID.
- No analytics or instrumentation.
- No Google posting automation.
- AI output is not validated for factual accuracy beyond the prompt guardrails — the user must review and edit.
- No auth, no user accounts.
- No rate limiting on the edge function beyond what the AI gateway enforces.
- Empty Supabase schema (no tables).
- ~50 shadcn/ui components installed, only ~10 used.
- No automated secret scanning in CI.
